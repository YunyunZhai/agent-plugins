## 前置检查（HTTP MCP）

本插件通过 HTTP 连接 gh-search MCP server（`http://127.0.0.1:18931/mcp`）。使用前确认：

1. gh-search 后端已启动：本机已运行
   `python -m app.mcp.mcp_server --http --port 18931`（见 user-guide「启动后端」）。
2. 若工具 `gh_search` 未出现在工具列表，向用户提示：
   请先启动后端并确认插件已安装、`/mcp` 中 gh-search 显示已连接。

# GitHub 智能开源项目搜索

根据用户的自然语言检索意图，先用 MCP 召回一批候选仓库，再按意图做**精选排序**输出 Top-N 推荐。

## 一、触发条件

当用户表达开源项目检索意图时触发，包括但不限于：

- "找开源项目" / "推荐开源库" / "GitHub 搜索"
- "找成熟活跃的 X 库" / "有没有能…的开源项目"
- "哪个开源项目适合做…"

## 二、意图识别

在对话中完成用户意图解析，输出三个决策：

### 2.1 通道选择

| 用户表述特征 | 通道 | 说明 |
|-------------|------|------|
| 含明确技术名词、仓库名、语言、框架 | `keyword` | GitHub GraphQL 实时搜索 |
| 模糊功能描述、"想找能…的"、"有没有…的项目" | `semantic` | 本地语义索引（qwen 嵌入） |
| 两者兼有，或想互补覆盖 | keyword + semantic 双通道 | 自行合并去重 |

### 2.2 Query 转写

将用户的中文意图转写为英文检索 query（GitHub 以英文为主）：

- **keyword 通道**：转写为 3~5 组具体英文关键词，空格拼成一条 query，每组 ≤4 词
  - 例：「找 Python 安全扫描库」→ `python security scanner SAST vulnerability detection`
  - **禁止万金油词**：`open source`、`tool`、`library`、`free software`、`self hosted`、`developer tools`、`machine learning`——这些词几乎匹配所有开源项目，引入大量噪音
- **semantic 通道**：直接传自然语言描述，如 `"a Python library for static security analysis and vulnerability scanning"`

### 2.3 意图标签

从用户表述中提取标签，影响后续排序和输出风格：

| 标签 | 触发词 | 影响 |
|------|--------|------|
| `mature` | "成熟"、"稳定"、"生产级"、"高星" | 偏重 star 数、活跃度 |
| `novel` | "新"、"最新"、"前沿"、"2025" | 偏重近期推送、新项目 |
| `performance` | "快"、"高性能"、"低延迟"、"轻量" | 偏重性能相关描述 |
| `popular` | "热门"、"大家都在用"、"主流" | 偏重 star 数和社区活跃 |
| `specific` | 含具体技术栈/协议/标准名 | 偏重精确匹配 |

## 三、MCP 调用

### 调用方式

```
MCP tool: gh_search(query, channel, top_k=300, language)
```

- `top_k` 固定 300，确保候选池够大
- 需要时两者都调（keyword + semantic），自行合并去重
- 合并去重和排序按用户意图灵活处理，不写死规则

### 错误处理

| 情况 | 处理 |
|------|------|
| MCP 返回 `isError` | 向用户说明错误，建议重试 |
| semantic 索引缺失 | 自动回退 `keyword` 通道 |
| 候选不足 100 | 跳过粗筛，全量进入精排 |
| 网络超时 | 提示用户重试 |

## 四、粗筛 Top-100

从 MCP 召回的约 300 个候选中快速筛选最相关的 100 个：

- 按用户意图相关性快速判断，不求精确，但求不遗漏
- `description` 为空**不能作为淘汰理由**（很多正经项目不填描述）
- 召回不足 100 时跳过粗筛，全部进入精排
- **Top-100 即为后续轮次的内存候选池**——用户追加约束时在这 100 个内操作，不重新调 MCP

## 五、精排 Top-N

对 Top-100 候选池做精细排序，输出最终推荐。

### 排序维度

按用户意图动态加权，综合判断，不搞固定公式：

- **相关性**：与用户意图的匹配程度（描述、topics、readme 片段）
- **成熟度**：star 数、近期推送、活跃度（用户要"成熟稳定"时加权）
- **新颖度**：近期创建/活跃、新技术栈（用户要"新/前沿"时加权）
- **专注度**：项目是否聚焦用户要的功能，而非大而全

### 注意

- semantic 通道返回的候选**没有 `stars` 字段**，不因此降级，用其他维度补足
- 每条推荐给出：仓库名（`owner/repo`）、star、一句话能力说明、匹配理由
- 默认 Top-10，用户要求"多推荐几个"时扩展到 Top-20
- 池内确实不够时如实说明，不凑数

## 六、输出格式

按用户意图动态调整呈现方式：

- 用户要"成熟稳定" → 突出 star 数、维护年限，标注【高星成熟】/【稳定维护】
- 用户要"新颖前沿" → 突出近期创建、新技术栈，标注【新锐项目】/【快速迭代】
- 用户要"高性能" → 突出性能相关描述，标注 benchmark/轻量等特征
- 默认：每条 = 仓库名 + star + 一句话能力说明 + 匹配理由，按相关性降序

## 七、后续轮次

用户追加反馈时，在 Top-100 内存池内操作，**不重新调 MCP**：

| 反馈类型 | 处理 |
|----------|------|
| 过滤："只要 Rust 的" / "stars 过 1000" | 池内字段过滤 |
| 重排："换个角度" / "更看重性能" | 调整排序维度重新精排 |
| 追问："第二个项目详细说说" | 直接展开详情 |
| 池内无匹配 | 明确告知，建议放宽条件或重新召回 |
| 全新主题（如从"安全扫描"切换到"网盘聚合"） | 重新走首轮流程（意图识别 → MCP 召回 → …） |

## 关键约束

1. **候选池是后续轮次的唯一数据源**——后续轮次不重新调 MCP，除非用户切换全新主题。
2. **不写文件**——候选池保留在对话上下文中，不写 `ghsearch_pool.json`。
3. **不调用外部脚本**——`enrich_metrics`、`rerank_results`、`llm_rank_results` 均不再使用，精排由大模型直接完成。
4. **`description` 为空不丢弃**——很多正经项目不填描述。
5. **规则从"死"变"活"**——不写死合并去重算法、排序公式，让大模型按意图灵活判断。
6. **semantic 通道无 stars**——不因此降级，用描述匹配度、readme 片段等其他维度补足。
